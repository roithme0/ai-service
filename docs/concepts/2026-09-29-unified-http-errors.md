# Unified HTTP Errors

## Status

Partially implemented. Session errors and framework-level 404s use the shared string-`detail` envelope. Application and framework validation errors now use structured `detail` items with `loc`, `msg`, and `type`. Unsupported methods and unhandled server failures remain for the final slice.

## Context

The conversation API uses typed Pydantic responses as the source for generated TypeScript types and Zod validators. Its session routes originally returned `ErrorResponse` with `kind` and an optional `turn_id`, or `InvalidInputResponse` with `kind` and `issues`. FastAPI supplied a separate `detail` body for unmatched routes, unsupported methods, and framework validation failures. The frontend transport classified another valid HTTP error body as an uncertain network response.

The [conversation API contract concept](2026-09-28-conversation-api-contract.md) establishes backend models and OpenAPI as the source for the frontend contract. This concept revises its error portion without changing successful responses or session behavior.

## Problem

A 404 from a matched session route and a 404 from an unmatched route have different bodies. The mismatch extends to 422: application validation uses either `issues` or only `kind`, while FastAPI's default validation body uses `detail`. A declared OpenAPI response model documents an endpoint response but does not transform framework-generated errors or validate a direct `JSONResponse`. Consumers must know which layer produced an error before they can parse it reliably.

## Proposed Direction

Use `detail` as the required field in every JSON error emitted by the application. Add a required, machine-readable `kind` to distinguish recovery behavior, and include `turn_id` only when a turn has been allocated. Do not retain the old `kind`-only or `issues` wire shapes. The response status remains the authoritative HTTP status; `kind` gives the client a stable distinction within that status.

Use two strict forms under that shared envelope:

- Ordinary errors have a nonempty string `detail`, a declared `kind`, and an optional nonempty `turn_id`.
- Validation errors have a nonempty array in `detail`. Each item contains only FastAPI's familiar `loc`, `msg`, and `type` fields with constrained types. Domain input issues map into this form with a stable domain type rather than a separate `issues` property. Framework validation details are normalized to these three fields; submitted `input` and variable `ctx` data are omitted.

For example, an unknown session could return `{"detail":"Session not found","kind":"unknown"}`. An invalid input could return `{"detail":[{"loc":["body","input"],"msg":"Invalid value","type":"value_error"}],"kind":"invalid_input"}`. Exact wording is not a contract; the structure and `kind` are.

Normalize FastAPI and Starlette errors at the application boundary, including unmatched routes, unsupported methods, request validation, and unhandled server failures. Give framework failures explicit kinds such as `not_found`, `method_not_allowed`, `request_validation`, and `internal_error`. A server failure must have a generic public detail; exception text stays in server logs. Existing application kinds can remain where they describe distinct session outcomes. The app cannot guarantee the shape of errors generated by a proxy or other infrastructure before a request reaches FastAPI.

Publish the app-owned error forms in OpenAPI, including the validation item shape. Keep direct error responses model-validated before serialization. Tests should compare representative runtime bodies with the published contract, including the framework paths that do not execute a session endpoint.

The shared schema constrains the set of `kind` values, but this change does not encode or enforce every allowed HTTP status–`kind` pair. Existing response status behavior remains covered by representative endpoint tests. Exhaustive pair validation is deferred to avoid multiplying OpenAPI variants and generated frontend types for this shape migration.

## Scope Boundaries

- Cover HTTP errors emitted by this FastAPI application, not only the four conversation operations. Successful response bodies and status codes are unchanged.
- Preserve `kind`-based recovery in the conversation controller. The frontend transport consumes the revised generated schemas and continues to distinguish a valid API error from a malformed response.
- Remove legacy parsing and serialization paths. Backend and frontend contract changes ship together; external consumers must update to the new shape.
- Keep domain validation details useful to callers. Do not expose internal exception strings, model inputs, secrets, or stack traces in public details.

## Integration Impact

The HTTP boundary in `backend/app/sessions/http.py` owns domain-to-error mapping. Application-level exception handlers in `backend/app/main.py` (or a small shared HTTP module) own framework error normalization. Both paths must emit the same envelope. OpenAPI generation changes the checked-in TypeScript and Zod contract, and `HttpConversationTransport` must parse the new forms. The frontend's `ApiErrorKind` and kind checks derive their allowed values from generated response types, so new kinds do not require a handwritten TypeScript list. Existing backend and frontend contract tests need updated expectations, plus coverage for an unmatched route, unsupported method, request validation, and server failure.

The conversation controller currently tests `kind` values such as `unknown`, `expired`, and `limit_reached` to decide whether a session is terminal. Keep those meanings. A framework-level `not_found` means the requested URL matched no route, so it remains distinct from `unknown` and must not trigger terminal-session recovery or offer a new-session action. The transport should report it as a valid API error, and the UI should present an API or configuration failure.

## Delivery Slices

The work is divided into end-to-end contract slices:

1. **Completed:** Add string `detail` to the shared session `ErrorResponse`, normalize unmatched-route 404s, regenerate the frontend contract, and keep route `not_found` separate from terminal session `unknown` in the controller. Representative runtime, schema, and frontend recovery tests cover both 404 paths.
2. **Completed:** Application and framework validation errors use structured `detail` items containing only `loc`, `msg`, and `type`. The `issues` wire shape is removed. Generated frontend types and validators are updated, and the transport applies strict object checks because generated Zod objects otherwise strip extra fields.
3. **Remaining:** Normalize other framework-generated errors, including unsupported methods and unhandled server failures, and verify their public bodies and logging behavior.

Each wire-format slice includes its backend and frontend changes before release. No legacy response parsing is retained.

## Alternatives Considered

- **Add `detail` only to current application errors:** fixes the common field but leaves framework errors without `kind` and validation under two structures.
- **Use only FastAPI's bare `detail`:** minimizes customization but loses the stable `kind` values used for session recovery and the optional `turn_id` needed for turn failures.
- **Wrap all validation errors in a string detail:** gives one scalar type but discards field-level information and diverges from FastAPI's usual validation response.

## Risks

- A global handler can accidentally convert unexpected failures into informative public messages or mask useful server logs. The 500 body should remain generic and logging must remain intact.
- FastAPI validation details can contain optional fields and arbitrary input values. Normalization must avoid leaking submitted content while retaining actionable locations and messages.
- A strict frontend parser will classify unrecognized error bodies as uncertain responses. This is correct for malformed app responses, but a proxy-generated error remains outside the app contract.

## Summary

All application-owned HTTP errors should carry FastAPI's `detail` field and a required `kind`, with optional `turn_id` for turn failures. Validation errors retain structured detail in FastAPI's `loc`/`msg`/`type` style. Application and framework paths, OpenAPI, generated validators, and frontend recovery must agree before release.
